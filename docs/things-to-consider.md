**Decided**

- *Trained components.* Two components are trained, in order: (1) the **retriever** (Qwen3-Embedding-0.6B + LoRA, ROPG-KD) and (2) the **query rewriter** (Qwen3-4B + LoRA, DPO). The generator remains frozen (a light-but-big API model). Training the retriever first ensures DPO preference pairs are built against a stable retriever.
- *Retriever.* Trained with **ROPG-KD** — now a core component, not a stretch. Qwen3-Embedding-0.6B fine-tuned offline via knowledge distillation from LLM judge scores (direct document scoring). ROPG-RL (online) remains out of scope. See Stage 1 in [methodology](methodology.md).
- *Generator personalization.* Persona-blind vs persona-aware is an experimental axis, not a fixed choice (the rewriter-redundancy question).
- *Retriever starting point.* Phase 0 uses lexical BM25 (SQLite FTS5). Qwen3-Embedding-0.6B is validated as the dense base (Rung 1) before ROPG-KD fine-tuning (Rung 3).
- *Rewriter policy model.* Qwen3-4B + LoRA.
- *ROPG-KD teacher signal.* Direct document scoring chosen over generation-mediated scoring. Rationale: direct scoring requires one judge call per `(query, persona, document)` triple vs. one generation + one judge call for generation-mediated, and avoids generation noise obscuring the document's intrinsic utility. The generation-mediated option is noted in [methodology](methodology.md) for completeness.
- *Data-generation judges.* **gpt-5.4-mini** for ROPG-KD teacher scoring, **gpt-5.4-nano** for DPO rewrite scoring; rewrite candidates are sampled from Gemma-4-E4B (the data-generation simulator); Qwen3-4B + LoRA is the policy being trained on those pairs. Rationale: price and generation time — the ROPG teacher scores 20 chunks per `(query, persona)` and warrants the stronger mini, while the DPO judge rates short rewrites where nano suffices. Per the guard-the-judge rule, the *evaluation* judge (still open above) must not reuse these models/prompts.
- *Generator access.* One OpenAI-compatible client serves both API models (OpenAI, Google AI Studio) and local servers (LMStudio, llama.cpp); the endpoint and key come from the `OPENAI_BASE_URL` and `OPENAI_API_KEY` environment variables, the model from config.
- *Checkpoint selection (ROPG-KD).* Best checkpoint = highest overall val Recall@K across personas (ties broken by lower val KD loss, then higher MRR) — not train/val KD loss alone. This guards against an encoder that minimises KL while degrading real retrieval (the reward-hacking check from Stage 1). Relevance for Recall@K/MRR is defined as the teacher's top-3 docs per `(query, persona)` group; alternatives considered are recorded in [methodology](methodology.md).
- *ROPG-KD encoder parity.* The training encoder must match the serving encoder exactly: Qwen3-Embedding native **last-token** pooling, documents encoded bare, queries wrapped as `Instruct: <profile>\nQuery: <text>`. Rationale: an earlier revision mean-pooled over a raw `<profile>\n\n<query>` string while `src/rag/embedder.py` served with last-token pooling, so the adapter was trained through one pooling head and read out through another — a silent loss with no error and a normal-looking loss curve. `benchmarks/check_encoder_parity.py` gates this at cosine ≥ 0.999 and must pass before any ROPG-KD result is reported. The same applies to `max_seq_length`, which must match between training and index build or the same chunk gets two different embeddings.
- *Embedder sequence length.* `embedder.max_seq_length: 2048` everywhere the encoder runs — ROPG-KD training, the parity gate, and every index build in `configs/phase*.yaml`. Rationale: at 512 the retriever saw only the head of a long chunk, so its embedding described the introduction rather than the passage the judge scored. The corpus p95 chunk is ~1.5k tokens, so 2048 fits all but the longest few whole; Qwen3-Embedding-0.6B supports far more, but activation memory scales with length and Kaggle's T4s have 16 GB. Settling the memory/throughput trade-off took two corrections worth recording: `training.doc_micro_batch` was first dropped 8 -> 2 on the mistaken belief that it caps peak activation memory. It does not — all micro-forwards stay in one autograd graph until `backward()`, so *retained* activations scale with tokens per step and only `batch_size` controls them; `doc_micro_batch` caps just the transient per-forward working set. The low value cost several-fold throughput by starving the T4 on 2-sequence launches. Final values: `batch_size: 2`, `doc_micro_batch: 10`, `eval.eval_batch_size: 32` (raised from 8 once it was clear eval encoding is `no_grad`, so it shares no constraint with training `batch_size`; it covers ~5% of an epoch's forwards on rank 0 alone and is not a throughput lever either way). All three are throughput/memory knobs that leave the optimizer step unchanged, whose effective batch is still `batch_size x world_size`. Raising the sequence length again means lowering `batch_size` — not `doc_micro_batch` — and rebuilding the index; see the parity note above.
- *ROPG-KD padding waste.* Measured with the real tokenizer over `data/ropg_kd/train.jsonl`: the 171 unique chunks have a median of **167 tokens** (p90 1487) and only 10 reach the 2048 cap, but `collate_scored` pads to the longest sequence in the whole batch, which is 2048 in the *median* batch. Roughly **65% of every FLOP was padding**. `encode_chunked` now sorts documents by true length before micro-batching and trims each micro-batch to its own width, restoring the caller's row order via an inverse permutation (both call sites `view(B, D, -1)` the result against `gold_scores`, so a lost permutation would silently misalign documents). The change is exact, not approximate: padding is already masked out of attention, `last_token_pool` reads the final token which left padding never touches, and RoPE encodes relative position so shifting every token left is invisible. Measured speedup at `batch_size: 2`: 1.68x at `doc_micro_batch: 20`, **2.21x at 10**, 2.54x at 5 — 10 keeps launches large enough not to starve the GPU. This inverts the earlier lesson: a smaller `doc_micro_batch` now buys real compute, not just a smaller transient buffer. No index rebuild or parity re-check is implied, since `max_seq_length` and the embeddings themselves are unchanged.
- *ROPG-KD gradient checkpointing is not a tunable.* Disabling it to gain throughput OOM'd at `batch_size: 2 / doc_micro_batch: 20` and again at `1 / 5`. Qwen3-Embedding-0.6B is 28 layers at hidden 1024, so retained activations run ~30 KB per token per layer in fp16 (~0.85 MB per token across the stack); one `batch_size: 1` step covers 21 sequences × 2048 padded tokens ≈ **36 GB**, against ~2.5 GB when only each block's input is stored. No `batch_size`/`doc_micro_batch` pair fits in a T4's 16 GB without it. Its cost is one extra forward (~33%), so removing it could never have returned more than 1.33x — well under the 2.2x the padding fix gives. `doc_micro_batch: 5` could not have rescued it either, since micro-forwards share one graph until `backward()`.
- *ROPG-KD retrieval metrics — nDCG primary, graded by teacher score.* Investigating a request to report `Recall@1..5` exposed a defect in the relevance definition rather than a missing column. Three measurements on `data/ropg_kd/val.jsonl` (276 groups × 20 judged docs) settled it: (1) teacher scores are strongly graded — mean by rank 0.757 / 0.569 / 0.447 / 0.372 / 0.323 — so a binary top-3 set counts the 1st and 3rd doc identically across a ~1.7× utility difference; (2) the boundary usually falls on a near-tie, with the rank-3 to rank-4 gap under 0.05 in **53%** of groups; (3) a score threshold would be worse, not better — at 0.7, 79/276 groups have no relevant doc and are skipped outright (125/276 at 0.8), discarding 17–45% of the val set. Top-*m* is the right structure for a *binary* metric, so the fix was to stop cutting: **nDCG@1..K with linear gain = raw `teacher_score`**, which has no boundary and ceiling 1.0 at every k — incidentally dissolving the original complaint, since `Recall@k` divides by *m* and could never exceed 1/3 at k=1. **Hit@1..K** is reported as the readable 0–1 curve, and **Recall@K + MRR** are kept unchanged: nDCG ranges over the same graded distribution the KD loss trains on, so the guard-the-judge rule wants a coarser, differently shaped metric beside it. All are slices of a ranking `evaluate_retrieval` already computed — no extra compute, no new data. **Open:** whether checkpoint selection should move from Recall@K to nDCG@K. It arguably should, but the current rule is Decided above and switching changes which adapter ships, so it is left as a deliberate hold. **Limitation, unchanged by this:** only 20 of 171 corpus chunks are judged per query, so a genuinely relevant but unjudged chunk scores 0 — the standard incomplete-judgments bias, which affected Recall/MRR identically before.
- *ROPG-KD epoch-0 baseline and paired significance testing.* Validation now runs once before training. This is not just convenience: PEFT zero-initializes `lora_B` and `eval_epoch` calls `model.eval()`, so a fresh adapter is **exactly the identity** and epoch-0 metrics *are* the frozen Qwen3-Embedding-0.6B — Rung 1 of the baseline ladder, measured through the same val set, relevance definition and code path as Rung 3, rather than reconstructed by hand from `notebooks/eval_ablation.ipynb`. It also exercises the whole eval path (corpus encoding, DDP all-reduce, rank-0 barrier, checkpoint dir) in minutes instead of after a two-hour epoch. Epoch 0 is **excluded from checkpoint selection** — an identity adapter winning would silently make every downstream Rung 3 number equal Rung 1 — with an explicit end-of-run `baseline -> best` comparison and a `WARNING` when nothing beat it, so a negative result stays loud. `evaluate_retrieval` also returns per-query vectors, persisted to `training_log.json`, because a mean supports a marginal CI but never a **paired** one: with 276 queries a single epoch's 95% CI is ≈ ±0.04, so epoch 1's 0.3406 and epoch 2's 0.3925 have overlapping marginal intervals and read as non-significant — while a paired bootstrap (same queries both times, per-query correlation ≈ 0.77) is ~35% tighter and puts that +0.052 near [+0.025, +0.079], excluding zero. Same data, opposite conclusion; overlapping error bars are a bad proxy for a paired test. One invariant the analysis rests on: pairing is **by position**, valid because group order and the skip decision depend only on the data, never on the model.
- *ROPG-KD LR scheduler warning.* `UserWarning: Detected call of lr_scheduler.step() before optimizer.step()` was **not** an ordering bug — `scaler.step(optimizer)` already precedes `scheduler.step()`. `GradScaler` starts at scale 65536, the first fp16 backward overflows, `scaler.step()` therefore skips the update and halves the scale, and PyTorch sees a scheduler step with no optimizer step behind it. Normal calibration; it fired once per rank at step 1. The only real consequence was the LR schedule advancing for updates that never happened (one or two steps out of 969). `train_epoch` now gates `scheduler.step()` on `scaler.get_scale() >= scale_before`, the standard idiom for detecting a skipped step.
- *ROPG-KD attention implementation.* `attn_implementation="sdpa"` is passed explicitly in `QwenEmbeddingModel`. Rationale: a 2×T4 run OOM'd on rank 1 partway through epoch 3 — after two clean epochs — trying to allocate **2.50 GiB** inside `backward()`. That figure is exactly `10 rows × 16 heads × 2048² × 4 bytes`, i.e. the attention score matrix for one `doc_micro_batch` at full width, upcast to fp32 by eager attention's `softmax(..., dtype=torch.float32)`, and allocated a second time during gradient checkpointing's backward recompute. The lesson worth keeping is *why it failed late*: peak memory scales with `rows × width²` and width is set by whichever documents the shuffle put in that batch, so with only 10 of 171 corpus chunks at the 2048 cap, most batches never approach the peak — `set_epoch` reshuffles and epoch 3 simply drew a bad one. Epochs 1–2 were lucky, not safe. This also bounds what the padding fix above could do: it cut the *linear* retained term ~2.9×, but the quadratic transient is untouchable by trimming, because those documents are genuinely 2048 tokens long. SDPA either drops the matrix entirely (mem-efficient kernel; flash needs sm_80, so not on a T4) or falls back to math, which materializes it in fp16 with no fp32 softmax — half the memory. Both outcomes clear this OOM, which is why no `try`/`except` softens it: a silent fall back to eager would resurface as the same OOM with nothing in the log. `train()` now logs peak allocated/reserved memory per epoch **on every rank**, so a flat series (worst-batch property) can be told apart from a climbing one (a real leak) without guessing. Contingency if SDPA lands on the math fallback and ~1.3 GiB of headroom proves thin: `doc_micro_batch` 10 → 5.
- *DDP launcher.* Multi-GPU ROPG-KD is launched with `torchrun` (a plain `!torchrun` cell, as in the supervisor's notebooks); the `torch.multiprocessing.spawn` path was removed. Rationale: the first 2x T4 attempt under spawn hung with no progress and no traceback, while torchrun surfaced a clean per-rank traceback on its first run — and torchrun is what the ecosystem and the supervisor's scripts assume. The likely cause of the hang was NCCL rendezvous, so the launch sets `NCCL_SHM_DISABLE=1` / `NCCL_P2P_DISABLE=1` (Kaggle's small `/dev/shm` and the absence of NVLink can stall NCCL's default transports; the bandwidth cost is irrelevant for ~5M LoRA gradients) and `init_process_group` uses a 10-minute timeout instead of NCCL's ~30-minute default, so a stall raises rather than hangs. `--standalone` picks a fresh rendezvous port per run so a crashed attempt cannot block the next. Consequence: `CFG` must be written to YAML before launch, since a fresh interpreter cannot be handed a Python dict — which also leaves each run reproducible from its config artifact. **Honest caveat:** the original hang was worked around, not root-caused; if DDP stalls again, start with `NCCL_DEBUG=INFO`.
- *ROPG-KD softmax temperatures.* student 0.05, teacher 0.2 (previously 1.0 for both). Rationale: student scores are cosine similarities in [-1, 1] and teacher scores lie in [0, 1]; at temperature 1.0 a softmax over 20 candidates is near-uniform on both sides, so the KD gradient carries almost no signal. Still to be confirmed by ablation — a reasoned default, not a measured optimum. See Stage 1 in [methodology](methodology.md).
- *`src/rl/scorer.py` status.* Superseded by the datagen notebook (`notebooks/gen_ropg_data.ipynb`) and `configs/datagen_ropg.yaml`, which now produce `data/ropg_kd/{train,val}.jsonl` directly. The module is kept only pending cleanup and should not be treated as the source of truth for the ROPG-KD scoring pipeline.
